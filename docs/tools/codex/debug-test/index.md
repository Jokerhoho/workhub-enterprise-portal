# 04 · 调试与测试

修复问题的核心顺序是：复现 → 缩小范围 → 找到根因 → 最小修复 → 回归测试。没有复现证据时，优先调查，不要同时尝试多个猜测。

## 提供一份可复现的问题

```text
问题现象：【用户看到什么】
复现步骤：
1. 【步骤】
2. 【步骤】
预期结果：【应该发生什么】
实际结果：【实际发生什么】
环境：【系统、版本、浏览器或配置】
相关日志：【完整错误，不只截最后一行】

请先复现并记录证据，再沿调用链定位根因。
不要先改代码；不要顺带升级依赖或重构。
```

## 五步调试

1. **复现**：确认相同步骤可以稳定触发。
2. **定位**：找到第一个偏离预期的位置。
3. **缩减**：去掉无关条件，得到最小失败用例。
4. **修复**：只改解决根因所需的部分。
5. **防回归**：写一个修复前失败、修复后通过的测试。

## 不要只看最后一条错误

让 Codex 检查：

- 完整堆栈中的第一个业务文件；
- 输入数据和边界条件；
- 最近相关差异；
- 配置和运行环境差异；
- 异步、缓存、并发和重试；
- 日志是否掩盖了原始错误。

## 测试分层

| 类型 | 证明什么 |
| --- | --- |
| 单元测试 | 一个函数或规则在边界输入下正确 |
| 集成测试 | 模块之间的契约真实可用 |
| 端到端测试 | 用户关键路径可完成 |
| 类型 / 静态检查 | 常见接口和语法错误被拦截 |
| 构建 | 生产打包链路可完成 |
| 人工验证 | 视觉、体验或外部环境行为符合预期 |

测试通过不等于问题一定解决；要确认测试覆盖原始失败条件。

## 修复后复核

```text
请证明这次修复解决了原始问题：
1. 展示修复前的失败条件；
2. 说明根因；
3. 指出最小代码差异；
4. 运行回归测试和相关测试；
5. 列出仍未覆盖的场景。
```

## 验收

- 有稳定复现或明确说明无法复现。
- 根因与症状之间有证据链。
- 修复范围最小。
- 回归测试覆盖原始失败。
- 相关测试、静态检查和构建按风险运行。
