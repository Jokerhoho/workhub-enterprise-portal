# 03 · 实现功能

Codex 最适合把清楚的需求推进成可验证变更。一个好任务同时说明用户结果、范围限制、异常情况和验证方法。

## 从需求到验收

不要只写“增加导出功能”。先定义：

- 谁在什么场景使用；
- 入口和完成后的可观察结果；
- 输入、空状态、错误和权限；
- 不能影响的现有行为；
- 需要运行的测试；
- 哪些动作仍需人工确认。

## 功能任务模板

```text
目标：【用户能完成什么】
用户场景：【角色、入口和触发条件】
验收标准：
- 【正常路径】
- 【空状态或错误路径】
- 【权限和数据边界】
范围限制：【不能改动的模块、兼容要求】
验证要求：【测试、构建、人工步骤】

请先检查现有实现和项目规则，给出简短方案与涉及文件。
确认方案后按最小可运行切片实现。不要重构无关代码。
完成后运行验证并汇总差异、证据和剩余风险。
```

## 用垂直切片推进

以“新增案例搜索”为例：

1. 先让现有数据能被搜索函数过滤。
2. 给搜索函数补正常、空词和无结果测试。
3. 接入输入框和结果数量。
4. 增加键盘、零结果和移动端状态。
5. 运行完整检查并审查差异。

每一步都能单独观察和回退，比一次性改数据、组件、样式和测试更容易发现问题。

## 实施过程中的三个暂停点

### 发现需求冲突

先列出冲突和选择，不替产品负责人决定。

### 需要新增依赖

说明为什么现有能力不够、依赖的维护与安全情况、包体或运行成本，再等待确认。

### 需要扩大范围

明确“原范围无法完成”的证据，比较最小扩展与替代方案，不静默修改其他模块。

## 完成摘要模板

```text
请按以下结构汇总：
- 用户现在可以做什么；
- 修改了哪些文件及原因；
- 运行了哪些验证及结果；
- 哪些边界未验证；
- 是否涉及配置、依赖、数据或部署；
- 建议的人工验收步骤。
```

## 验收

- 所有验收标准都有对应实现或测试。
- 差异不夹带无关重构。
- 新旧行为边界清楚。
- 错误、权限和空状态被覆盖。
- 用户结果经过实际运行或明确的人工步骤验证。
