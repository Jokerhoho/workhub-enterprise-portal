# 08 · 自动化、安全与交付

团队使用 Codex 的目标不是让所有操作自动化，而是让重复工作更快、关键决策更清楚、每次交付都有证据。权限越大、影响范围越广，验证和审批就越严格。

## 交付闸门

| 阶段 | Codex 可以完成 | 人工确认重点 |
| --- | --- | --- |
| 分析 | 梳理需求、代码、风险与方案 | 范围和业务判断 |
| 实现 | 修改代码、测试和文档 | 核心逻辑与边界 |
| 验证 | 运行检查、构建、审查差异 | 证据是否充分 |
| 提交 | 整理原子提交与说明 | 变更归属 |
| 推送/合并 | 按授权执行 Git 操作 | 远端、分支、保护规则 |
| 发布 | 执行明确的发布流程 | 环境、窗口、回退方案 |
| 观察 | 汇总日志、指标和异常 | 是否继续或回退 |

不要把“允许改代码”理解为同时允许推送、合并和发布。每个外部动作都应有明确目标与授权。

## 权限与联网

- 默认只开放完成任务所需的文件、命令和网络范围。
- 运行来源不明脚本、安装依赖或访问外部地址前检查来源与影响。
- 生产密钥使用组织的密钥管理方式，不写入提示词、日志或仓库。
- 数据删除、数据库迁移、权限变更和公开发布必须有预览与回退路径。
- 自动化任务记录输入、版本、执行结果和失败原因，便于追踪。

## 自动化任务模板

```text
目标：【本次交付的用户结果】
环境：【本地 / 测试 / 预发布 / 生产】
允许动作：【明确列出】
必须暂停确认：【依赖安装、迁移、推送、发布等】
验证闸门：【测试、构建、审查、安全检查】
成功标准：【可观察指标】
失败与回退：【停止条件、恢复方式、负责人】

先只读检查现状并列出计划。每通过一个闸门再继续；
任何目标、权限或影响范围变化时暂停，不自行扩大授权。
```

## 三个完整案例

### 案例一：企业门户改版

1. 只读识别页面、内容来源、构建和部署配置。
2. 把改版拆成导航、首页、教程、响应式和部署五个切片。
3. 每片运行文档测试与公网配置构建。
4. 审查全部差异，确认无旧品牌、死链和敏感联系方式。
5. 人工验收后提交；推送触发部署，再检查线上首页和关键路径。

### 案例二：线上缺陷修复

1. 用脱敏日志和稳定步骤复现。
2. 先补失败测试，再实施最小修复。
3. 运行相关测试和受影响模块回归。
4. 审查错误处理与安全边界，准备回退提交。
5. 在发布窗口上线，观察错误率和关键业务指标。

### 案例三：依赖与安全更新

1. 说明漏洞、受影响版本和项目是否实际使用该路径。
2. 比较最小版本升级、替换依赖和临时缓解方案。
3. 在隔离分支更新锁文件，运行测试、构建和依赖检查。
4. 审查行为变化与部署风险，不把其他升级混入。
5. 经负责人批准后合并，并记录验证与后续观察项。

## 团队落地清单

- 为核心仓库建立准确的 `AGENTS.md`。
- 固定任务模板、审查格式和完成摘要。
- 定义哪些命令可自动运行，哪些动作必须批准。
- 将测试、构建、类型检查和安全检查接入持续集成。
- 对高风险仓库采用分支保护、评审人和发布审批。
- 每月复盘失败任务，更新规则、Skills 和案例。
- 用完成时间、返工率、缺陷逃逸率衡量效果，而不是只看生成代码量。

## 最终交付清单

- 用户结果和验收标准全部对应到证据。
- 工作区、分支、远端和部署环境准确。
- 测试、构建、审查与必要安全检查通过。
- 配置、迁移、依赖、权限和数据影响已说明。
- 提交可回退，发布有停止条件和恢复步骤。
- 线上关键路径和指标已检查，剩余风险有负责人。
