# 06 · Worktrees 并行任务

Git worktree 可以让同一个仓库同时拥有多个独立工作目录。它适合并行推进互不依赖的任务，但不会自动消除逻辑冲突：真正的关键是任务边界、文件所有权和合并顺序。

## 什么时候值得并行

适合：

- 一个任务补文档，另一个任务修独立模块；
- 一路研究方案，另一路做小型实现；
- 多个问题拥有不同入口和测试范围；
- 长时间任务不应阻塞当前工作区。

不适合：

- 两个任务会频繁修改同一批文件；
- 后一个任务依赖前一个尚未确定的接口；
- 需求仍在快速变化，验收边界不清；
- 任务太小，协调成本高于执行成本。

## 并行任务设计表

| 工作区 | 单一目标 | 主要文件 | 验证 | 依赖 |
| --- | --- | --- | --- | --- |
| A | 修复登录超时 | 认证模块、相关测试 | 单测 + 登录回归 | 无 |
| B | 补管理员文档 | 文档目录 | 文档构建 + 链接检查 | A 的最终行为说明 |
| C | 调研缓存方案 | 只读报告 | 证据与方案比较 | 无 |

如果“主要文件”大量重叠，应改为串行或先定义共享接口。

## 标准工作流

1. 从已同步、状态明确的基线开始。
2. 每个 worktree 只承担一个目标，并使用能说明任务的分支名。
3. 在任务提示中写清文件范围、验收标准、禁止动作和验证命令。
4. 各工作区独立运行测试、审查差异并提交。
5. 按依赖关系决定合并顺序；每次合并后重新运行受影响检查。
6. 成果确认后再清理已完成工作区。

## 可直接复制的并行任务模板

```text
你当前负责并行任务：【单一目标】
基线：【分支或提交】
允许修改：【目录或文件】
不要修改：【共享模块或其他任务范围】
验收标准：【可观察结果】
验证要求：【测试或构建】

先检查范围是否与其他任务冲突；若需要越界，暂停并说明原因。
完成后汇总修改文件、验证证据、提交信息、合并依赖和剩余风险。
```

## 冲突预防规则

- 数据结构、公共类型、路由和锁文件指定单一负责人。
- 不在多个工作区同时升级依赖或批量格式化。
- 公共接口先确定契约，再让下游任务开始。
- 合并前同步最新基线，不以“本地测试通过”替代集成验证。
- 删除工作区前确认提交已在目标分支或仍可找回。

## 一个实用案例

企业门户同时要“新增教程、修复搜索、核对部署”。可以这样拆：

1. 内容工作区只新增 Markdown 与图片。
2. 搜索工作区只改索引、组件和相关测试。
3. 部署工作区先只读检查构建配置，输出风险与修改建议。
4. 先合并内容，再合并搜索并跑整站构建，最后处理部署配置。

这样可以减少内容和代码互相阻塞，也把高风险部署动作留到最终确认。

## 验收

- 每个工作区都有唯一目标和文件边界。
- 基线、依赖关系和合并顺序已记录。
- 每个分支可独立解释、测试和回退。
- 集成后重新运行了受影响的完整检查。
- 已完成工作区在确认成果可恢复后再清理。
