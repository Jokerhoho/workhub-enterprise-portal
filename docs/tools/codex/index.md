# Codex 快速上手

Codex 适合在代码仓库中理解结构、实现需求、修复问题、运行检查和审查变更。它不是“说完需求就自动上线”的黑盒：清晰的范围、可验证的验收标准、权限边界和人工审查仍然是可靠交付的关键。

::: tip 适合从这里开始
第一次使用时，选择一个范围明确的小任务，例如解释一个模块、补充一个测试、修改一处页面文字，或定位一个有稳定复现步骤的问题。
:::

## 适用场景

| 场景 | 可以交给 Codex 做什么 | 人工重点检查 |
| --- | --- | --- |
| 熟悉项目 | 梳理目录、入口、依赖和关键调用链 | 结论是否有代码证据 |
| 实现功能 | 按要求修改代码、补测试、更新文档 | 边界情况、兼容性、产品逻辑 |
| 修复问题 | 复现、定位原因、做最小修复并验证 | 是否真正解决根因 |
| 代码审查 | 检查差异、发现回归风险、给出建议 | 风险等级与业务影响 |

## 5 分钟完成第一个任务

1. 在 Codex 中打开目标项目，先确认当前目录和允许修改的范围。
2. 先让 Codex 说明项目结构与可能涉及的文件，不急着修改。
3. 提供目标、现状、验收标准、不能改动的部分和需要运行的检查。
4. 让 Codex完成修改和验证，并汇总改了什么、为什么、验证结果与剩余风险。
5. 查看代码差异；确认无误后再提交、推送或部署。

## 可直接复制的任务模板

### 熟悉一个陌生项目

```text
请先只读分析这个项目，不要修改文件。
说明：
1. 项目的用途、技术栈和启动入口；
2. 主要目录及职责；
3. 一个用户请求从入口到结果的关键调用链；
4. 本地运行和测试方式；
5. 你仍不确定、需要我补充的信息。
每个重要结论请指出对应文件。
```

### 实现一个小功能

```text
目标：【要实现的功能】
用户场景：【谁在什么情况下使用】
验收标准：
- 【可观察结果 1】
- 【可观察结果 2】
范围限制：【不能改动的模块、兼容要求】
验证要求：【需要运行的测试或构建】

请先检查现有实现并给出简短方案，然后直接完成修改、运行验证，最后汇总变更和剩余风险。
```

### 修复一个问题

```text
问题现象：【看到什么】
复现步骤：【按顺序列出】
预期结果：【应该发生什么】
实际结果：【实际发生什么】
相关日志：【如有】

请先复现并定位根因，再做范围最小的修复；补充能防止回归的测试，并说明验证结果。不要顺带重构无关代码。
```

## 验收清单

- 代码差异只覆盖约定范围，没有夹带无关改动。
- 构建、测试、类型检查或格式检查已按项目要求运行。
- 新增行为有测试或清晰的人工验证步骤。
- 错误处理、权限、输入边界和兼容性已检查。
- 提交、推送、合并、发布等外部动作经过负责人确认。

## 安全边界

不要把生产密钥、口令或客户敏感数据写入提示词、日志或仓库。修改权限控制、依赖、部署配置、数据库结构或 CI/CD 时应提高审查等级。运行来源不明的脚本、访问外部网络、删除数据和发布代码前，必须核对目标与影响范围，并保留可回退方案。
