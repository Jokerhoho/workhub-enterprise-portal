# Codex 快速上手

Codex 适合在代码仓库中理解结构、实现需求、修复问题、运行检查和审查变更。它不是“说完需求就自动上线”的黑盒：清晰的范围、可验证的验收标准、权限边界和人工审查仍然是可靠交付的关键。

::: tip 适合从这里开始
第一次使用时，选择一个范围明确的小任务，例如解释一个模块、补充一个测试、修改一处页面文字，或定位一个有稳定复现步骤的问题。
:::

## 适用场景

| 场景 | 可以交给 Codex 做什么 | 人工重点检查 |
| --- | --- | --- |
| 熟悉项目 | 梳理目录、入口、依赖和关键调用链 | 结论是否有代码证据 |
| 实现功能 | 按要求修改代码、补测试、更新文档 | 边界情况、兼容性、产品逻辑 |
| 修复问题 | 复现、定位原因、做最小修复并验证 | 是否真正解决根因 |
| 代码审查 | 检查差异、发现回归风险、给出建议 | 风险等级与业务影响 |

## 5 分钟完成第一个任务

1. 在 Codex 中打开目标项目，先确认当前目录和允许修改的范围。
2. 先让 Codex 说明项目结构与可能涉及的文件，不急着修改。
3. 提供目标、现状、验收标准、不能改动的部分和需要运行的检查。
4. 让 Codex完成修改和验证，并汇总改了什么、为什么、验证结果与剩余风险。
5. 查看代码差异；确认无误后再提交、推送或部署。

## 可直接复制的任务模板

### 熟悉一个陌生项目

```text
请先只读分析这个项目，不要修改文件。
说明：
1. 项目的用途、技术栈和启动入口；
2. 主要目录及职责；
3. 一个用户请求从入口到结果的关键调用链；
4. 本地运行和测试方式；
5. 你仍不确定、需要我补充的信息。
每个重要结论请指出对应文件。
```

### 实现一个小功能

```text
目标：【要实现的功能】
用户场景：【谁在什么情况下使用】
验收标准：
- 【可观察结果 1】
- 【可观察结果 2】
范围限制：【不能改动的模块、兼容要求】
验证要求：【需要运行的测试或构建】

请先检查现有实现并给出简短方案，然后直接完成修改、运行验证，最后汇总变更和剩余风险。
```

### 修复一个问题

```text
问题现象：【看到什么】
复现步骤：【按顺序列出】
预期结果：【应该发生什么】
实际结果：【实际发生什么】
相关日志：【如有】

请先复现并定位根因，再做范围最小的修复；补充能防止回归的测试，并说明验证结果。不要顺带重构无关代码。
```

## 三个可直接落地的案例

### 案例一：接手陌生网站并安全改版

1. 先只读梳理入口、页面、样式、构建和部署方式。
2. 把需求拆成“内容、结构、视觉、交互、部署”五组验收标准。
3. 每次只完成一个可验证切片，例如先改导航，再改首页，再补响应式。
4. 每个切片运行测试和构建，最后统一审查差异。
5. 由负责人确认后再提交、推送与发布。

### 案例二：把零散需求变成可验收功能

```text
请先把下面需求转成实现清单，每项包含用户结果、涉及范围、验收方式和风险。
确认清单后按最小可运行切片实现；每完成一片就运行相关测试。
最后使用 /review 审查未提交变更，只报告有代码证据的问题。
需求：【粘贴需求】
```

### 案例三：并行处理互不干扰的任务

当“补文档、修一个独立问题、研究第三方接口”彼此没有文件冲突时，可以使用独立工作区并行推进；每个工作区只承担一个目标。合并前分别运行验证，再按依赖顺序汇总，避免多个任务同时改同一处代码。

## 推荐工作节奏

需求拆解 → 制定计划 → 小步实现 → 自动测试 → 代码审查 → 提交复盘。复杂任务不要一次生成全部代码；把每一步变成能观察、能测试、能回退的交付点。

## 验收清单

- 代码差异只覆盖约定范围，没有夹带无关改动。
- 构建、测试、类型检查或格式检查已按项目要求运行。
- 新增行为有测试或清晰的人工验证步骤。
- 错误处理、权限、输入边界和兼容性已检查。
- 提交、推送、合并、发布等外部动作经过负责人确认。

## 安全边界

不要把生产密钥、口令或客户敏感数据写入提示词、日志或仓库。修改权限控制、依赖、部署配置、数据库结构或 CI/CD 时应提高审查等级。运行来源不明的脚本、访问外部网络、删除数据和发布代码前，必须核对目标与影响范围，并保留可回退方案。
