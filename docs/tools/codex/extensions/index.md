# 07 · Skills、Plugins 与 MCP

扩展 Codex 前先判断问题属于“规则、流程还是连接”。选对载体，团队才容易复用、审核和维护。

## 四种能力怎么选

| 方式 | 解决什么 | 典型例子 | 维护重点 |
| --- | --- | --- | --- |
| `AGENTS.md` | 这个仓库应如何工作 | 测试命令、目录边界、代码规范 | 与仓库同步更新 |
| Skill | 一类任务的可复用方法 | 发布检查、写迁移、生成周报 | 指令清晰、示例可验证 |
| Plugin | 打包多种扩展能力 | 某团队的 Skills、连接和命令合集 | 版本、权限与来源 |
| MCP | 连接外部工具和数据 | GitHub、工单、数据库、内部 API | 凭据、工具范围与审计 |

简单判断：只约束当前项目用 `AGENTS.md`；反复执行同一种工作用 Skill；要分发一整套能力用 Plugin；必须读取或操作外部系统时再接 MCP。

## 写好项目规则

仓库根目录的 `AGENTS.md` 可以说明：

- 项目结构与禁止修改区域；
- 安装、运行、测试和构建命令；
- 代码、文档和提交规范；
- 哪些操作必须人工确认；
- 完成任务时必须提供的验证证据。

规则应短、具体、可执行。目录内存在更具体的规则时，让它只覆盖该区域的特殊要求，避免重复和冲突。

## 设计第一个 Skill

从高频、边界稳定、可以验收的流程开始，例如“网站发布前检查”：

```text
目标：在不发布的前提下完成网站发布前检查。
步骤：确认工作区 → 安装状态 → 测试 → 公网配置构建 → 链接检查 → 差异审查。
输出：每项结果、失败原因、剩余风险、建议发布动作。
限制：不得推送、修改远端设置或执行发布。
```

Skill 中应把判断标准写清楚，并尽量复用脚本、模板和样例；不要只写一段宽泛提示词。完成后用一个正常案例、一个边界案例和一个失败案例验证。

## 安装与使用扩展的安全检查

1. 确认来源、维护者、版本和最近更新情况。
2. 阅读 Skill 指令或 Plugin 清单，了解会调用哪些能力。
3. 检查 MCP 暴露的工具、数据范围和写权限。
4. 在测试项目或只读模式先运行一次。
5. 不把生产密钥写进仓库、提示词或示例。
6. 定期移除不用的连接并轮换凭据。

## MCP 连接任务模板

```text
目标：【需要从外部系统读取或执行什么】
允许的数据范围：【项目、表、目录或资源】
允许的动作：【只读 / 新建草稿 / 更新指定对象】
禁止动作：【删除、批量修改、发布等】
确认点：【哪些写操作必须先预览并等待批准】
审计输出：【记录对象、时间、结果和失败】
```

连接成功不代表权限设计完成。先列出可用工具，使用最小数据样本验证，再逐步开放写入能力。

## 在本门户中沉淀能力

发现值得复用的 Skill 或 Agent 后，可以进入 [Skills 平台](/skills/)：记录适用场景、来源、安装方式、权限、使用模板、案例和验证结果。团队内部技能还应注明负责人和版本，避免“能安装但没人维护”。

## 验收

- 扩展类型与问题相匹配，没有为了简单任务引入过重能力。
- 指令、输入、输出、限制和失败处理完整。
- 外部连接遵循最小权限并可追踪。
- 安装方式、版本和维护责任清楚。
- 正常、边界和失败案例均已验证。
