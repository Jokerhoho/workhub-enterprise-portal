# 05 · 代码审查与 Git

代码写完不等于任务完成。可靠的交付需要先审查差异、验证行为，再把相关修改组织成边界清楚的提交。推送、合并和发布是不同动作，应分别确认。

## 审查什么

一次有效审查重点寻找会影响用户或系统的具体问题：

- 功能是否偏离验收标准；
- 错误、空状态、权限和输入边界是否遗漏；
- 是否引入兼容性、性能或安全回归；
- 测试是否真正覆盖新增行为；
- 配置、文档和部署步骤是否同步；
- 差异中是否夹带与任务无关的修改。

不要把个人风格偏好和确定性缺陷混在一起。每条问题都应指出文件、触发条件、影响和建议处理方式。

## 三种常用审查范围

| 审查对象 | 适用时机 | 重点 |
| --- | --- | --- |
| 未提交变更 | 本地开发完成后 | 遗漏、误改、调试残留 |
| 相对目标分支的全部差异 | 合并请求前 | 完整业务影响与跨提交问题 |
| 指定提交 | 回看单次变更 | 提交是否原子、说明是否准确 |

在 Codex CLI 中可使用 `/review` 发起审查，并选择未提交变更、目标分支差异或指定提交。桌面应用中也可以直接要求它审查当前差异。

## 可直接复制的审查任务

```text
请审查当前任务相对【目标分支或未提交状态】的全部差异。
验收标准：【粘贴验收标准】

只报告有代码证据、可能影响正确性、安全、性能或维护的具体问题。
每条说明：严重程度、文件位置、触发条件、用户或系统影响、建议修复。
不要直接修改代码；最后补充仍未覆盖的测试风险。
```

收到结果后，逐条验证。确认的问题再单独要求修复，并重新运行相关测试；不要把“审查”和“自动接受全部建议”合成一步。

## 提交前工作流

1. 查看工作区状态，确认只包含本任务文件。
2. 阅读完整差异，删除临时日志、测试数据和意外格式化。
3. 运行项目规定的测试、类型检查和构建。
4. 使用 `/review` 或明确提示审查差异。
5. 只暂存相关文件，形成一个可以独立解释和回退的提交。
6. 再确认远端与目标分支，随后推送。

## 好提交的标准

- 一个提交解决一个清楚的问题；
- 标题说明结果，而不是笼统写“update”；
- 代码、测试和必要文档一起提交；
- 不包含密钥、生成缓存、大型无关文件；
- 回退该提交不会破坏另一个独立功能。

提交说明可以采用：`类型(范围): 用户可观察结果`，例如 `fix(search): preserve filters after refresh`。

## Git 操作模板

```text
请先只读检查当前分支、远端、工作区状态和完整差异。
告诉我哪些文件属于本任务、哪些可能是无关改动，并列出应运行的验证。
完成验证后，为本任务建议一个原子提交方案和提交说明。
未经我确认，不要推送、合并、改写历史或发布。
```

## 发现混合改动时

如果工作区已有其他人的修改，先识别归属，不要覆盖或回退。能够按文件或变更块安全拆分时，只纳入本任务；无法区分时暂停并请求负责人确认。不要为“保持整洁”而清除未知修改。

## 验收

- 审查范围和目标分支准确。
- 每条问题都有可复现条件与文件证据。
- 测试结果与未覆盖风险均已记录。
- 提交只包含本任务内容且可以独立回退。
- 推送、合并和发布均指向确认过的目标。
